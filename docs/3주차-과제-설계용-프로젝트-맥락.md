# 3주차 과제 설계를 위한 프로젝트 맥락

아래는 제가 1·2주차 리액트 리팩터링 실습에 사용한 프로젝트의 현재 상태입니다. 이 내용을 바탕으로 기존 프로젝트에 이어서 진행할 수 있는 3주차 과제를 설계해 주세요.

- 저장소: https://github.com/dlsrksrhk/next-refactor-study
- 기준 코드: `main`, `03d7018` — 빠른 수정 조회 실패 재시도 병합

- 과제의 **왜 바꿔야 하는지(why)**, **현재 무엇이 문제인지**, **변경 후 사용자 경험**을 먼저 설명해 주세요.
- 처음에는 요구사항과 단계별 힌트를 주고, 정답 코드와 완성 구현은 제가 요청할 때 제공해 주세요.
- 한 번에 한 가지 핵심 주제를 다루고, 기존 코드와 연결되는 구체적인 상황으로 설명해 주세요.

## 2. 애플리케이션의 업무 맥락

그룹웨어의 **사내 전체 게시판**입니다. 직원이 공개된 게시글을 읽고 자신이 작성한 글을 수정합니다.

- 로그인 사용자는 `김동현`, ID는 `employee-001`로 고정되어 있습니다. 실제 로그인 기능은 없습니다.
- 샘플 게시글 `101`, `102`는 김동현의 글입니다.
- `103`은 다른 직원의 글이며 조회만 가능합니다.
- 프론트엔드는 내 글에만 수정 기능을 노출하고, 백엔드도 다른 직원의 글 수정 요청을 거부합니다.
- 저장은 공개 게시글에 즉시 반영됩니다. 비공개 초안, 임시 저장, 자동 저장 기능은 없습니다.
- 글 작성·삭제·검색·필터·페이지네이션 기능은 현재 없습니다.

### 화면과 사용자 흐름

| 경로·기능 | 현재 동작 |
| --- | --- |
| `/board` | 게시글 목록과 내 글의 빠른 수정 버튼 |
| `/board/articles/[id]` | 게시글 상세 조회 |
| `/board/articles/[id]/edit` | 내 글을 전체 화면에서 수정 |
| 목록의 빠른 수정 | URL을 유지한 채 네이티브 `<dialog>` 팝업에서 수정 |

전체 편집의 기본 동작은 저장 성공 토스트 후 상세 화면으로 이동하는 것입니다. ‘저장 후 이 화면에서 계속 편집’을 선택하면 저장 후에도 편집 화면에 머무릅니다.

빠른 수정은 팝업을 열 때 단일 게시글을 다시 조회합니다. 목록을 본 이후 서버 내용이 바뀌었을 수 있기 때문입니다. 조회 중에는 ‘게시글을 불러오는 중입니다.’를 표시하고, 성공한 뒤 입력 폼을 생성합니다.

편집을 시작한 뒤에는 사용자 입력을 유지합니다. 취소하고 다시 열면 저장하지 않은 입력을 버리고 서버 내용을 새로 가져옵니다. 저장 성공 시에만 팝업을 닫고 `router.refresh()`로 목록을 갱신합니다. 실패하면 입력과 팝업을 유지합니다.

## 3. 기술과 실행 구조

- npm workspaces로 프론트엔드와 백엔드를 분리했습니다.
- 프론트엔드: Next.js App Router `16.4.2`, React `19.3.1`, TypeScript.
- 스타일: 일반 CSS, Prettier, ESLint. 토스트: Sonner.
- 백엔드: Node.js의 기본 HTTP 서버, JavaScript ES Modules(`.mjs`).
- 저장소: 로컬 JSON 파일. 별도 DB·ORM은 없습니다.
- 별도 전역 상태 관리·서버 상태 조회 라이브러리·폼 라이브러리는 사용하지 않습니다.
- Node.js 22 이상, Windows·PowerShell·WebStorm 환경에서 실습합니다.

페이지는 Server Component로 초기 데이터를 조회하고, 편집 컴포넌트는 Client Component로 상태·이벤트를 처리합니다. 브라우저의 `/api` 요청은 Next.js rewrite를 통해 별도 백엔드에 전달됩니다. 데이터 조회는 `cache: "no-store"`를 사용합니다.

Next.js 관련 변경이 필요하면 설치된 버전의 `node_modules/next/dist/docs/`를 확인하도록 프로젝트에 지침이 있습니다. 과거 버전의 API를 전제로 과제를 설계하지 말아 주세요.

```text
frontend/src/
  app/
    board/page.tsx
    board/articles/[id]/page.tsx
    board/articles/[id]/edit/page.tsx
    globals.css
  features/articles/
    article.ts            # Article, ArticleDraft, User 타입
    getArticle.ts         # Server Component에서 사용하는 조회 함수들
    article-api.ts        # 브라우저의 상세 GET·수정 PUT 함수
    useSaveArticle.ts     # 저장 실행·진행 상태·즉시 중복 실행 방지
    ArticleEditor.tsx     # 전체 편집 폼과 저장 후 이동 정책
    QuickEditButton.tsx   # 팝업 열기·닫기, 성공 후 목록 갱신
    PopupEditor.tsx       # dialog와 상세 조회·로딩·오류·재시도
```

`getArticle.ts`와 `article-api.ts`에 동명의 `getArticle`이 있지만 실행 환경과 오류 계약이 다릅니다. 서버용은 404에서 `null`을 반환하고, 브라우저용은 정상 응답이 아니면 예외를 던집니다.

## 4. 데이터 모델과 API 계약

```ts
type Article = {
  id: string;
  title: string;
  body: string;
  authorId: string;
  authorName: string;
  createdAt: string;
  updatedAt: string;
};

type ArticleDraft = Pick<Article, "title" | "body">;
type User = { id: string; name: string };
```

| API | 계약 |
| --- | --- |
| `GET /api/me` | 고정 사용자 JSON |
| `GET /api/articles` | `Article[]` |
| `GET /api/articles/:id` | `Article`, 없으면 404 |
| `PUT /api/articles/:id` | `{ title, body }` 요청, 성공 시 본문 없는 204 |

제목은 공백만으로 저장할 수 없습니다. 잘못된 입력은 400, 다른 직원의 글 수정은 403입니다. 저장 시 제목·본문·수정일을 갱신합니다.

저장 성공은 JSON 파일 기록 완료를 의미합니다. 파일 기록이 실패하면 500을 반환하고 메모리의 기존 데이터도 유지합니다. 새로고침하거나 서버를 재시작해도 저장 내용이 유지됩니다.

`articles.seed.json`은 저장 파일이 없는 첫 실행에만 복사합니다. 이미 존재하는 `articles.json`을 덮어쓰지 않습니다. 과제 준비 중 기존 로컬 수정 데이터를 초기화하지 않아야 합니다.

## 5. 1주차 완료 내용: 커스텀 훅의 책임 분리

처음에는 저장 관련 여러 책임이 하나의 훅에 섞여 있었고, 다음 구조로 리팩터링했습니다.

| 계층 | 현재 책임 |
| --- | --- |
| API 함수 | HTTP 호출과 응답 상태 검사 |
| 저장 훅 | API 함수 호출, 진행 상태, 중복 실행 방지, 처리 결과 반환 |
| 화면 컴포넌트 | 입력·검증·토스트·이동·팝업 닫기 등 사용자 상호작용 |

현재 훅 이름은 **`useSaveArticle`**입니다. 이전 이름인 `useArticleEditor`를 기준으로 과제를 만들지 말아 주세요.

```ts
type SaveResult =
  | { status: "success" }
  | { status: "error"; message: string }
  | { status: "already-saving" };

// useSaveArticle()의 반환 계약
type SaveArticleController = {
  isSaving: boolean;
  save: (articleId: string, draft: ArticleDraft) => Promise<SaveResult>;
};
```

- `isSaving` state는 화면의 저장 중 표시와 입력 비활성화를 담당합니다.
- ref는 같은 훅 인스턴스에서 렌더링 전 즉시 반복 호출되어도 중복 요청을 막습니다.
- 성공·실패 후 잠금을 해제하며, 이미 저장 중인 호출에는 추가 토스트를 띄우지 않습니다.
- 훅은 입력 상태·검증·토스트·라우터를 소유하지 않습니다.
- HTTP 4xx·5xx와 네트워크 실패는 저장 실패로 처리합니다. 현재 훅의 사용자 메시지는 공통 메시지입니다.
- UI가 저장 결과를 보고 성공 시에만 이동하거나 닫습니다.

토스트는 일반 화면의 `root` 호스트와 dialog 내부의 `popup` 호스트를 사용합니다. 네이티브 dialog의 top layer 때문에 팝업 안에도 호스트가 있습니다. 팝업 오류는 같은 메시지 ID를 갱신하며, 저장할 때마다 dismiss 후 재생성하지 않습니다.

저장 중 취소 버튼은 비활성화되지만 **Esc로 닫기는 허용**합니다. 닫힌 폼의 늦은 저장 응답은 `isActiveRef` 검사로 토스트·닫기·목록 갱신에 반영하지 않습니다. 브라우저에서 팝업을 닫는 것과 서버 저장을 취소하는 것은 별개입니다.

## 6. 2주차 완료 내용: useEffect 오남용 개선

시작 코드의 문제는 다음 두 가지였습니다.

1. 렌더링마다 새로 만드는 `request` 객체를 Effect 의존성으로 사용해, 응답 → 상태 갱신 → 재조회가 반복됐습니다.
2. 폼에서 `[article]` Effect로 제목·본문을 계속 서버 값에 맞춰, 사용자 입력을 덮어썼습니다.

현재는 다음과 같이 개선했습니다.

- `PopupEditor`가 단일 게시글을 조회하고, 조회 성공 후에만 `QuickEditForm`을 마운트합니다.
- 조회 Effect 의존성은 `[articleId, retryFlag]`입니다.
- 폼의 제목·본문은 `useState(article.title)`, `useState(article.body)`로 최초 마운트 시 초기화합니다. 서버 값과 계속 동기화하는 Effect는 제거했습니다.
- Effect 내부에서 새 `AbortController`를 만들고, cleanup에서 해당 요청을 취소합니다.
- `.then()`과 `.catch()`는 `controller.signal.aborted`이면 결과를 반영하지 않습니다.
- 조회 실패 화면에는 다시 시도·닫기가 있습니다.
- 재시도는 `setRetryFlag((prev) => !prev)`와 오류 초기화를 수행합니다. 같은 ID에서도 Effect가 다시 실행됩니다.
- 최초 조회 실패 시 `article`은 `null`이므로, 오류를 비우면 폼 대신 ‘게시글을 불러오는 중입니다.’가 표시됩니다.
- Strict Mode의 초기 추가 실행과 끝없는 반복 조회를 구별하며, 매 Effect 실행마다 새 controller를 사용합니다.

`QuickEditButton`은 목록의 각 행에 있으며, 목록 행은 `article.id`를 key로 사용합니다. 팝업은 `isOpen`일 때만 렌더링되어 닫으면 언마운트됩니다. 현재 UI에는 **열린 팝업 안에서 다른 글로 대상을 전환하는 기능이 없습니다.** 101을 닫고 102를 열면 다른 팝업 인스턴스로 시작합니다.

따라서 현재 구조에서 팝업의 별도 `key` 누락을 미해결 버그로 볼 필요는 없습니다. 향후 하나의 팝업 인스턴스를 유지하면서 ID만 바꾸는 기능을 과제에 추가한다면, 로딩 상태·폼 초기화·이전 대상 응답 처리를 새롭게 검토해야 합니다.

## 7. 오류·지연 재현과 테스트 환경

화면에 실습용 패널을 넣지 않고, 백엔드 환경 변수로 재현합니다. 설정 변경 후 백엔드를 재시작해야 합니다.

| 대상 | 상태 옵션 | 지연 옵션 | 기본값 (상태 / 지연) |
| --- | --- | --- | --- |
| 목록 조회 | `READ_LIST_STATUS` | `READ_LIST_DELAY_MS` | `200` / `0`ms |
| 단일 조회 | `READ_DETAIL_STATUS` | `READ_DETAIL_DELAY_MS` | `200` / `1000`ms |
| 저장 | `SAVE_STATUS` | `SAVE_DELAY_MS` | `204` / `0`ms |

조회 상태는 `200`·`500`, 저장 상태는 `204`·`500`, 지연은 0~30000ms를 지원합니다. 목록과 단일 조회의 실패는 서로 독립적입니다. 단일 조회 오류 설정은 빠른 수정뿐 아니라 전체 편집·상세 화면의 조회에도 적용됩니다.

```sh
npm run dev          # 프론트엔드 3000
npm run dev:backend  # 백엔드 4000, 별도 터미널
npm run lint
npm run typecheck
npm run format:check
npm test
```

현재 테스트는 백엔드 7개·Playwright 브라우저 15개, 총 22개가 통과했습니다. 주요 검증은 다음과 같습니다.

- 권한·API 응답, 파일 저장과 재시작 후 유지.
- 저장 중 중복 요청 방지·입력 잠금·실패 후 재저장.
- 전체 편집의 저장 후 이동·계속 편집.
- 팝업 저장 성공 후 닫기·목록 갱신, 취소 후 입력 초기화.
- 입력 중 재조회 방지와 입력 보호.
- 조회 실패 → 재시도 중 로딩 → 재실패 또는 성공.
- 조회 중 Esc로 닫을 때 요청 취소와 다시 열기.
- 101의 입력을 취소하고 102를 열 때 상태 분리.
- 닫힌 팝업의 늦은 저장 실패 응답 무시.
- 목록·단일 조회의 독립적인 지연·실패 설정.

브라우저 테스트는 별도 포트 3100·4100과 별도 JSON 저장 파일을 사용해 실제 로컬 데이터를 보호합니다.

## 8. 3주차 과제를 설계할 때 요청하는 내용

1. 위의 현재 구조에서 자연스럽게 이어지는 주제를 정하고, 이번에 배울 핵심 개념을 밝혀 주세요. 1·2주차의 해결된 버그를 다시 과제로 내지 말아 주세요.
2. 실제 직원이 겪을 문제나 새 요구사항을 제시하고, 변경 전후의 사용자 흐름을 설명해 주세요.
3. 현재 파일명을 기준으로 수정 대상과 각 파일의 책임을 안내해 주세요.
