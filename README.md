# 사내 전체 게시판

그룹웨어에서 직원이 전 직원에게 공유한 게시글을 확인하고, 자신이 작성한 글을 수정하는 예제입니다. 로그인 사용자는 **김동현**으로 고정되어 있습니다. 회사명은 예시로 한빛 그룹웨어를 사용합니다.

## 실행

Node.js 22 이상이 필요합니다. 프로젝트 루트에서 설치합니다.

```sh
npm install
```

터미널 두 개에서 각각 실행하세요.

```sh
# 터미널 1: 목업 백엔드 (4000)
npm run dev:backend
```

```sh
# 터미널 2: Next.js 프론트엔드 (3000)
npm run dev
```

[사내 전체 게시판](http://127.0.0.1:3000/board)을 여세요. 기존 서버가 실행 중이면 종료 후 다시 시작하세요.

## 업무 흐름

- `/board`: 전체 게시글 목록입니다. 내 글에만 빠른 수정 버튼이 표시됩니다.
- `/board/articles/101`: 내 글의 제목·본문·작성자·수정일을 확인합니다.
- `/board/articles/101/edit`: 전체 편집 화면입니다. 기본은 저장 알림 후 상세 이동이며, ‘저장 후 이 화면에서 계속 편집’을 선택하면 화면에 머무릅니다.
- 빠른 수정: 목록 위에 팝업을 열어 수정합니다. URL을 유지하고 저장 요청 종료 후 목록을 다시 조회합니다.
- 다른 직원의 글은 조회만 가능합니다. 백엔드도 다른 직원의 글 수정 요청에 403을 반환합니다.

두 편집 방법은 같은 게시글과 `PUT /api/articles/:id`를 사용합니다. **모든 저장은 공개 게시글에 즉시 반영**됩니다. 비공개 임시 저장이나 초안 기능은 없습니다.

## 읽을 코드

```text
frontend/src/
  app/
    board/page.tsx                         # 게시글 목록
    board/articles/[id]/page.tsx           # 게시글 상세
    board/articles/[id]/edit/page.tsx      # 조회·작성자 확인 → 편집기에 전달
  features/articles/
    article.ts                            # 게시글·사용자 타입
    getArticle.ts                         # 백엔드에서 게시글·목록·사용자 조회
    ArticleEditor.tsx                     # 전체 편집 + 계속 편집 체크박스
    BoardList.tsx                         # 목록 표와 검색·내 글 필터 (3주차 시작 코드)
    QuickEditButton.tsx                   # 목록에서 팝업 열기 + 목록 갱신
    PopupEditor.tsx                       # 빠른 수정 팝업, 상세 조회와 요청 정리
    QuickEditForm.tsx                     # 빠른 수정 입력과 저장
    article-api.ts                        # 브라우저 상세 조회·수정 요청과 응답 상태 검사
    useSaveArticle.ts                     # 저장 실행·진행 상태·중복 호출 방지
    formatDate.ts                         # 한국 시간 기준 수정일 표시
backend/
  articles.seed.json                      # Git으로 관리하는 초기 샘플
  articles.json                           # 로컬 영구 저장소 (Git 제외)
  server.mjs                              # 서버 시작
  routes.mjs                              # URL·HTTP 메서드 → 처리 함수 연결
  article-handlers.mjs                    # 조회·수정 요청, 권한·입력 확인
  article-store.mjs                       # 게시글 JSON 저장·조회
  http.mjs                                # JSON 응답·요청 본문 읽기
```

초기 데이터 조회는 Server Component가 HTTP로 수행하고, 입력·저장은 Client Component에서 처리합니다. 브라우저의 `/api` 요청은 Next.js 설정을 통해 백엔드로 전달됩니다. 서버 데이터는 별도로 캐시하지 않습니다.

## 3주차 실습: 검색·필터 결과의 중복 상태 (30~45분)

목록에 **제목 검색**, **내 글만 보기**, **검색 결과 건수**를 추가한 실습 시작 버전입니다.
`board/page.tsx`는 Server Component를 유지하며 게시글과 사용자를 `BoardList`에 전달합니다.
기존 빠른 수정·조회·저장 코드는 그대로 사용하고, 의도적인 결함은 새 `BoardList.tsx`에만 있습니다.

### 시작 버전에서 재현할 문제

- 검색 결과 배열과 건수를 각각 state로 보관합니다.
- 검색어 변경은 제목 조건만 적용하여 내 글 필터를 반영하지 않습니다.
- 내 글 필터를 해제하면 입력된 검색어와 무관하게 전체 게시글을 표시합니다.
- 체크박스 변경은 결과 건수를 갱신하지 않습니다.
- 저장 후 새 게시글 배열이 전달되어도 검색 결과에는 이전 내용이 남습니다.

실제 로컬 JSON과 seed는 초기화하지 않습니다. 현재 데이터의 제목·작성자를 기준으로 확인하세요.
검색어를 비워 전체 목록을 표시한 뒤 내 글만 보기를 켜면, 행 수와 건수가 달라지는 현상을 쉽게 볼 수 있습니다.
검색 후 빠른 수정으로 제목을 바꾸면 실제 저장은 성공하지만 목록에는 이전 제목이 남습니다.
페이지를 새로고침하면 서버에서 저장된 내용을 확인할 수 있습니다.

검색 입력·체크박스·저장 후 갱신에서 어떤 정보를 함께 맞춰야 하는지 살펴보세요.

### 완료 조건

- 제목 검색은 앞뒤 공백과 영문 대소문자를 무시합니다.
- 검색어가 비면 제목으로 제한하지 않고, 검색과 내 글 조건은 동시에 적용합니다.
- 조건을 조작하는 순서가 달라도 최종 결과와 건수가 같습니다.
- 빈 결과는 0건과 ‘검색 조건에 맞는 게시글이 없습니다.’를 표시합니다.
- 검색·체크박스 조작 자체는 HTTP 조회를 발생시키지 않습니다.
- 저장 후 `router.refresh()`로 새 데이터가 전달되면 현재 조건으로 목록과 건수를 표시합니다.
- 갱신 시 검색어와 체크 상태를 유지하고, 결과 동기화를 위한 Effect는 추가하지 않습니다.
- 기존 저장 실패·취소·Esc·늦은 응답 무시 정책을 유지합니다.

새 라이브러리·전역 상태·커스텀 훅은 필요하지 않습니다. 선택 과제는 검색 조건 초기화 버튼입니다.
`PopupEditor`, `QuickEditForm`, `useSaveArticle`은 필수 실습 수정 대상이 아닙니다.

### 시작 상태 검증

`npx playwright test tests/week3-starter.spec.ts`는 위 결함이 재현되는지 확인하는 테스트입니다.
실습 완료 시 올바른 검색·필터·갱신 동작을 검증하도록 바꿉니다.
기존 테스트는 제거하거나 비활성화하지 않습니다. 시작 버전에서는 목록의 새 제목을 확인하는
기존 저장 후 갱신 검증이 중복 상태 결함을 잡아내므로 실패할 수 있습니다.
전체 테스트가 모두 통과해야 한다는 완료 조건은 리팩터링을 끝낼 때 적용합니다.

준비 상태 검증에서는 백엔드 7개와 브라우저 15개가 통과했고, 아래 기존 테스트 3개가
저장 후 새 제목을 찾는 단계에서 예상대로 실패했습니다. 새로 추가한 결함 재현 테스트 3개는 통과했습니다.

- `article-save.spec.ts`: popup 즉시 중복 호출·500 실패 후 재시도
- `article-save.spec.ts`: 네트워크 실패 후 팝업 재저장
- `articles.spec.ts`: 빠른 수정 저장 후 목록 갱신·취소 입력 초기화

이 세 항목도 실습을 마치면 다시 통과해야 하며, 테스트를 삭제하거나 검증을 약화하지 않습니다.

## 목업 API

### 2주차: 빠른 수정 팝업의 useEffect 리팩터링 (30~45분)

시작 코드에 있던 **반복 조회와 입력값 덮어쓰기 문제를 해결**했습니다.
조회 의존성은 게시글 ID이며, 입력 폼은 마운트할 때만 서버 값으로 초기화합니다.
조회 Effect마다 `AbortController`를 만들고 정리 시 요청을 취소하며, 취소된 요청의 결과는 반영하지 않습니다.
조회 실패 시 다시 시도와 닫기를 제공하며, 재시도 중에는 로딩 화면을 표시합니다.
저장 훅은 1주차 구현을 유지합니다.

1. 두 서버를 실행하고 `/board`에서 `101`의 빠른 수정을 엽니다.
2. 개발자 도구 Network에서 `articles/101`로 필터링합니다.
3. 약 1초 뒤 입력 폼이 나타나면 본문을 바꿔보세요.
4. 입력하는 동안 GET이 반복되지 않고 수정한 본문이 유지되는지 확인하세요.
5. 취소 버튼으로 팝업을 닫으세요.

김동현의 글은 `101`, `102`이고, 다른 직원의 글은 `103`입니다.
기존 `backend/articles.json`이 있으면 seed 변경이 자동 반영되지 않으므로,
`102`의 `authorId`와 `authorName`만 `employee-001`, `김동현`으로 맞추면 됩니다.

상세 GET에만 기본 1초 지연을 적용했습니다. 백엔드 실행 전에
PowerShell에서 `$env:READ_DETAIL_DELAY_MS = "1000"`으로 조절할 수 있습니다(0~30000ms).
목록 조회 지연은 `READ_LIST_DELAY_MS`로 설정하며 기본값은 0입니다.

조회 조건 정리, 폼 초기화 Effect 제거, 조회 요청 정리와 실패 후 재시도를 완료했습니다.
목록의 각 행은 게시글 ID를 key로 사용하고, 팝업은 행마다 별도로 생성되며 닫을 때 언마운트됩니다.
다른 게시글을 열 때 이전 편집 상태를 공유하지 않습니다.

#### 목표와 수정 범위

정책은 **팝업을 열 때 최신 서버 내용으로 편집을 시작하고, 편집 중에는 사용자 입력을 유지**하는 것입니다.
취소하고 다시 열면 저장하지 않은 입력을 버리고 서버 내용을 다시 가져옵니다.

| 파일 | 실습할 책임 |
| --- | --- |
| `frontend/src/features/articles/PopupEditor.tsx` | 상세 조회 조건, 로딩·오류·재시도, 이전 조회 응답 정리 |
| `frontend/src/features/articles/QuickEditForm.tsx` | 편집 시작 시 입력 초기화, 이후 사용자 입력 보호 |
| `frontend/src/features/articles/QuickEditButton.tsx` | 열기·닫기와 편집 대상별 상태 구분 |

`article-api.ts`의 상세 조회 함수는 준비되어 있으며 선택적인 `AbortSignal`을 받습니다.
`useSaveArticle`은 수정 대상이 아닙니다. 기존 `success`, `error`, `already-saving` 계약과 토스트 방식을 유지합니다.
전체 편집·목록·상세 화면도 유지하며, 자동 저장·새 조회 라이브러리·실습용 화면은 추가하지 않습니다.
저장 중 Esc로 닫기와 닫힌 폼의 저장 응답 무시도 기존 정책을 유지합니다.

#### 단계별 진행

1. **현상 관찰:** 본문을 바꾸고 Network에서 GET 응답이 올 때 입력이 어떻게 바뀌는지 기록합니다.
2. **조회 조건:** 팝업의 조회 Effect가 어떤 값의 변화를 감지해야 하는지 정하고 반복 조회를 해결합니다.
3. **입력 보호:** 조회 결과와 작성 중인 입력의 수명을 구분하고, 입력 초기화가 필요한 시점을 정합니다.
4. **조회 정리:** 조회 중 닫기·다시 열기·다른 글 편집 시 이전 요청의 결과를 처리하지 않도록 합니다.
5. **실패 대응:** 조회 실패 화면에 다시 시도와 닫기를 제공하고, 재시도 중에는 폼을 표시하지 않습니다.

1~5단계의 필수 구현을 완료했습니다.
같은 게시글의 재조회는 재시도 상태의 변경으로 실행하며, 새 요청마다 controller를 생성합니다.
의존성 검사 규칙을 끄거나 근거 없이 빈 배열로 바꾸지 않습니다.

#### 완료 조건

- 팝업을 연 뒤 입력하거나 부모가 재렌더링되어도 불필요한 GET과 입력 덮어쓰기가 없습니다.
- 조회 중에는 입력 폼이 없고, 성공한 뒤에 표시됩니다.
- 취소 후 같은 글을 다시 열면 서버 내용을 새로 가져옵니다.
- `101`을 닫고 `102`를 열면 이전 글이나 입력이 남지 않습니다.
- 조회 중 닫고 다시 열어도 이전 응답이 현재 팝업에 영향을 주지 않습니다.
- 조회 실패 후 재시도·닫기가 가능합니다.
- 저장 실패 시 입력·팝업을 유지하고, 성공 시에만 닫기·목록 갱신을 수행합니다.

개발 모드에서 초기 Effect가 추가 실행되는 현상과 응답마다 끝없이 조회하는 문제는 구분합니다.

`npx playwright test tests/week2-query.spec.ts`는 입력 유지와 불필요한 재조회 방지,
조회 실패 후 재시도, 조회 중 닫기의 요청 취소와 다시 열기, 다른 글의 편집 상태 분리를 검증합니다.
기존 저장 테스트도 함께 사용합니다.

| 메서드 | 주소 | 응답 |
| --- | --- | --- |
| GET | `/api/me` | 고정 로그인 사용자 김동현 |
| GET | `/api/articles` | 게시글 목록 |
| GET | `/api/articles/:id` | 게시글 상세, 없으면 404 |
| PUT | `/api/articles/:id` | 내 글 수정, 성공 시 본문 없는 204 |

수정 본문은 `{ "title": "제목", "body": "본문" }`입니다. 작성자와 작성일은 바뀌지 않고 수정일만 갱신됩니다. 공백 제목은 400, 다른 사람의 글 수정은 403을 반환합니다.

게시글은 `backend/articles.json`에 저장합니다. PUT 요청이 성공하면 제목·본문·수정일이 이 파일에 기록되므로 **새로고침하거나 백엔드를 재시작해도 유지**됩니다. 파일 기록이 실패하면 500을 반환하고 조회용 메모리도 변경하지 않습니다. 서버가 종료된 상태에서는 이 JSON 파일을 직접 편집할 수도 있습니다.

`backend/articles.seed.json`은 초기 샘플로 Git에 커밋합니다. `backend/articles.json`은 실행 중 바뀌는 로컬 데이터이므로 Git에서 제외합니다. 백엔드는 저장 파일이 없는 첫 실행에만 초기 샘플을 복사하며, 이미 저장된 데이터는 덮어쓰지 않습니다. 샘플 변경은 별도로 커밋할 수 있고 기존 로컬 데이터에 자동으로 반영되지는 않습니다.

초기화가 필요하면 백엔드를 종료하고 `articles.json`을 다른 이름으로 백업한 뒤 다시 실행하세요. 새로운 저장 파일이 샘플에서 생성되며 백업은 직접 복원할 수 있습니다.

로그인 기능을 실제로 구현한 것은 아니며 `/api/me`와 서버의 작성자 검사는 고정 사용자 기준으로 동작합니다.

## 지연·실패 재현

화면에 실습 패널을 넣지 않고 백엔드 환경 변수로만 제공합니다. 백엔드를 종료한 뒤 **백엔드용 PowerShell 터미널**에서 설정하고 다시 실행하세요.

| 조회 대상 | 응답 상태 옵션 | 지연 옵션 | 기본값 (상태 / 지연) |
| --- | --- | --- | --- |
| 목록 `GET /api/articles` | `READ_LIST_STATUS` | `READ_LIST_DELAY_MS` | `200` / `0`ms |
| 단일 게시글 `GET /api/articles/:id` | `READ_DETAIL_STATUS` | `READ_DETAIL_DELAY_MS` | `200` / `1000`ms |

상태 옵션은 `200`, `500`, 지연 옵션은 0~30000ms를 허용합니다.
기존 `READ_STATUS`, `READ_DELAY_MS`는 각각 `READ_DETAIL_STATUS`, `READ_DETAIL_DELAY_MS`로 이름을 바꿨습니다.

```powershell
# 상세 조회를 1초 지연한 뒤 500 반환 (목록 조회·저장은 정상)
$env:READ_LIST_STATUS = "200"
$env:READ_DETAIL_DELAY_MS = "1000"
$env:READ_DETAIL_STATUS = "500"
npm run dev:backend
```

```powershell
# 목록 조회만 500 반환 (상세 조회·저장은 정상)
$env:READ_LIST_STATUS = "500"
$env:READ_DETAIL_STATUS = "200"
npm run dev:backend
```

존재하지 않는 게시글은 기존대로 404입니다.
상세 조회 설정은 빠른 수정뿐 아니라 전체 편집·상세 화면에도 적용됩니다.
팝업에서 오류가 표시되면 백엔드를 종료하고 `READ_DETAIL_STATUS`를 `200`으로 바꿔 다시 실행한 뒤,
팝업의 **다시 시도**를 눌러 성공 흐름을 확인하세요. 설정은 서버 시작 시 읽으므로 변경 후 재시작이 필요합니다.

```powershell
# 저장 응답을 2초 지연
$env:SAVE_DELAY_MS = "2000"
$env:SAVE_STATUS = "204"
npm run dev:backend
```

```powershell
# 저장 시 500 반환 (게시글은 수정하지 않습니다)
$env:SAVE_DELAY_MS = "0"
$env:SAVE_STATUS = "500"
npm run dev:backend
```

정상 동작으로 돌아갈 때는 서버를 종료하고 `SAVE_DELAY_MS`를 `0`, `SAVE_STATUS`를 `204`로 설정한 뒤 다시 시작하세요. 네트워크 실패는 브라우저 개발자 도구의 Network Offline으로 재현할 수 있습니다.

## 현재 저장 구조

입력 상태·제목 검증·토스트·화면 이동과 팝업 닫기는 각 편집 화면이 담당합니다. `article-api.ts`는 React에 의존하지 않고 PUT 요청과 응답 상태 검사만 수행합니다.

`useSaveArticle()`은 입력값을 받아 저장하고 `success`, `error`, `already-saving`을 반환합니다. state는 화면의 저장 중 표시, ref는 같은 훅 인스턴스의 즉시 중복 호출 차단에 사용합니다. 이미 저장 중인 호출은 추가 요청이나 토스트 없이 무시합니다. 성공·실패 후에는 잠금을 해제해 재시도할 수 있습니다.

전체 편집은 성공 후 상세로 이동하거나 계속 편집할 수 있습니다. 팝업은 성공 시에만 닫히며 실패하면 입력을 유지합니다. 저장 중 Esc로 팝업을 닫을 수 있고, 닫힌 팝업의 늦은 응답은 새 팝업의 안내나 닫기에 영향을 주지 않습니다. 팝업 닫기가 서버에 이미 전달된 저장의 취소를 보장하지는 않습니다.

테스트는 별도 목업 백엔드(4100)와 프론트엔드(3100)를 실행하고 종료합니다. 브라우저 테스트는 `backend/.data-test/articles.json`, 백엔드 테스트는 임시 폴더의 JSON을 사용하므로 실제 `backend/articles.json`은 변경하지 않습니다. 테스트용 저장 파일도 없으면 `articles.seed.json`에서 생성합니다.

브라우저 테스트는 정상 저장·계속 편집·빠른 수정·작성자 권한과 함께 공백 제목 검증, 즉시 중복 호출 시 단일 요청, 저장 중 입력 잠금, 500·네트워크 실패 후 재시도, 닫힌 팝업의 늦은 응답 무시를 확인합니다. 백엔드 테스트는 최초 샘플 복사, 서버 재시작 후 데이터 유지와 파일 기록 실패를 확인합니다.

## 프론트엔드 코드 스타일

`sweet-commerce`의 Prettier 기준을 적용했습니다. 줄 너비 100자, 들여쓰기 2칸, JSX 속성은 한 줄에 하나씩 표시합니다. 이 프로젝트는 일반 CSS를 사용하므로 Tailwind 정렬 플러그인은 포함하지 않습니다.

프로젝트 루트 또는 `frontend` 폴더에서 다음 명령을 사용할 수 있습니다. 루트 명령도 프론트엔드만 대상으로 실행됩니다.

```sh
npm run format        # 코드 포맷 적용
npm run format:check  # 포맷 검사
npm run lint          # Next.js·React·TypeScript 코드 검사
```

ESLint와 Prettier가 충돌하지 않도록 `eslint-config-prettier`를 적용했습니다. 생성된 파일과 빌드·테스트 결과물은 검사 대상에서 제외합니다.

WebStorm에서 저장할 때도 적용하려면 Settings → Languages & Frameworks → JavaScript → Prettier에서 자동 설정을 선택하고 **Run on save**를 켜세요. 프론트엔드의 `.prettierrc.json`을 사용하도록 설정하면 됩니다.

백엔드의 PUT 처리 흐름은 `server.mjs` → `routes.mjs` → `article-handlers.mjs`의 `handleUpdateArticle()` → `article-store.mjs`의 `updateArticle()` 순서입니다. 수정 동작을 읽으려면 `handleUpdateArticle()`부터 보시면 됩니다.
